# data-forge · 创平数智工场

源码仓库：[henryxu1008/data-forge](https://github.com/henryxu1008/data-forge)。

**前端交互原型，尚未连接真实后端。** 模拟预标注、训练、评测、推理、部署、权限、API 授权和资源调度不是实际模型效果或服务器能力；无需配置模型密钥。package.json 的 private:true 只防止误发布到 npm，与 GitHub 可见性无关。

## 运行与构建

使用 Node.js 24；本轮干净检出验证使用 Node.js 24.22.1。

```bash
npm ci
npm run dev -- --host 127.0.0.1
```

开发地址以终端输出为准，通常为 http://127.0.0.1:5173/。

```bash
npm run build
npm run preview -- --host 127.0.0.1 --port 4173 --strictPort
```

构建后预览地址为 http://127.0.0.1:4173/。本仓库没有部署步骤；.openai/hosting.json 仅保留原构建入口需要的空 d1/r2 配置。

## 测试与自动化 CI

从仓库中的应用初始状态可以重建合成测试会话，无需找回历史用户快照：

```bash
npm ci
npm run test:all
npm run test:static
npm run test:ai-static
npm run test:governance-static
```

`test:all` 的前置步骤会依次生成 base/P1/AI 合成会话并构建；`test:governance-static` 的前置步骤会重建上游会话并生成治理合成会话。生成的 `examples/`、本地证据 JSON、`tmp/`、`output/` 和构建产物保持忽略，不上传仓库。它们用于可复演测试，不是恢复的历史数据。`test:source` 为无需外部会话的较小回归集合。

浏览器脚本使用独立 Chromium 上下文。首次安装与复演示例：

```bash
npx --no-install playwright install --with-deps chromium
npm run test:delivery-browser
npm run test:work-orders-browser
npm run test:sampling-browser
npm run test:approvals-browser
npm run test:deadlines-browser
npm run test:correction-retry-browser
npm run test:changes-browser
npm run test:model-knowledge-browser
```

每个浏览器 npm 入口先生成自己的合成会话。已有兼容 Chromium 时可设置 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`。静态检查与浏览器测试应分开运行，避免静态输出触发开发服务器刷新。

`.github/workflows/prototype-ci.yml` 在所有目标分支的 PR（含 Draft）创建、更新、重开、转待评审或修改时运行，也检查后续 main 提交；默认分支存在此工作流后可手动运行。核心任务负责构建、逻辑和静态检查，浏览器矩阵独立执行上述 8 个场景；矩阵中一个失败仍保留其余场景结果。日志、截图及合成验收证据保留 7 天。`Acceptance gate` 仅在核心任务和全部浏览器场景成功时通过，未配置失败放行或自动重试。

工作流使用 Node.js 24、锁文件安装和与 Playwright 版本匹配的 Chromium，没有部署步骤。旧 PR #9–#16 分支尚未包含新工作流，不能把本轮 CI 结果描述为它们各自已获得远端绿灯；组合基线通过后再按依赖顺序评审。此变更没有修改 main 分支保护规则；是否将 `Acceptance gate` 设为必需检查由仓库管理员在评审后配置。

## 功能范围

需求/指标版本、多源汇聚与冲突、独立增强、版本化质量规则、文本/图片标注审核发布；模型版本绑定和批量模拟 AI 标注；模拟训练评测与服务；文档问答/知识索引/智能体反馈闭环；立项责任、许可审批撤回、样本防污染和效果/成本证据。

IndexedDB 保存当前浏览器会话，跨电脑需用户自行导出/导入。存储 key 和内部演示 ID 保持兼容，example.com 邮箱与演示占位凭据均不是真实账号。当前没有 OCR、真实模型调用、训练权重、GPU 调度、服务器鉴权或外部服务接入。

离线单 HTML 导出需要先构建，然后运行 Python 3 标准库脚本 python scripts/make-portable.py。字体重新子集化另需 fontTools；普通启动和构建不需要 Python。

### 交付与验收原型（PR #9）

数模服务中心新增“交付与验收”。先发布通过质检的数据版本，并完成共享用途准入，再选择另一位具有该项目审核权限的成员作为客户验收人。登记外部交付包证据后提交，由指定成员签收或退回；退回后选择修订版本补交，原单与版本快照保留。已签收订单支持反馈、关联补交和处理关闭。工作台汇总交付待办，完整会话保存/恢复包含交付状态。

这是本地模拟流程：不传输文件、不发送客户通知、不提供服务器鉴权或真实客户签名。校验和与外部材料引用为人工登记，未验证文件内容。运行 `npm run build` 后执行 `npm run test:source`；专项测试为 `npm run test:delivery`。`npm run test:all` 会先从应用初始数据生成合成会话、运行 P1/AI 场景并构建，再执行全量测试；生成数据不是恢复的历史用户会话。单独生成示例可运行 `npm run test:fixtures`。浏览器验收使用 `npm run test:delivery-browser`，首次需 `npx playwright install chromium`；已有兼容 Chromium 时可设置 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`。测试使用独立浏览器上下文，覆盖退回、补交、跨角色签收、反馈关闭、刷新恢复、空间隔离和移动端宽度。

### 生产工单与售后纠错（Issue #1，依赖 PR #9）

数据生产中心新增“生产工单”。负责人为整个未发布批次指定不同的标注人、审核人和期限；标注员领取后沿用现有文本/图片工作台操作，全部样本提交后进入批次审核。审核人逐条复核并运行质检，再通过工单验收，之后才允许发布。退回可提起争议，由第三位具备项目审核权限的成员决定继续返工或重新审核；仲裁不会自动通过样本。超时转派为负责人手工操作，保留历史。

交付页面的未关闭售后反馈可生成独立纠错批次及工单。纠错覆盖原冻结版本的全部记录，通过来源版本/记录 ID 保留关系，不继承原批次的 AI 预测接受状态。关联后必须以该工单验收后发布的版本补交，客户签收后才能关闭反馈。

验证命令：`npm run test:work-orders`、`npm run test:work-orders-browser`（Chromium 配置同交付浏览器测试）。旧批次未纳入工单时维持原流程。当前支持全量复核后的随机批次抽检；已支持可选三级独立审核；自动调度/通知和真实后端仍待建设；原型完成范围及未实现扩展以当前验收基线为准。

### 批次抽检与复检（Issue #1，依赖 PR #10）

创建工单时可启用抽检，配置比例、最低样本数和合格率阈值，分派后策略不可变更。先完成逐条审核及规则质检，再由指定审核人冻结随机抽检名单、样本内容与修订。样本数取比例向上取整与最低数量的较大值，上限为批次总数；使用 Web Crypto 随机洗牌，无放回抽取。每项结论需填写依据且不可覆盖，完成全部判定后计算合格率，不做四舍五入后比较。

不合格或数据变更后不能验收，也不能重新抽名单碰运气；必须退回返工、完成审核和质量检查，再启动新修订复检。历史轮次、失败依据及退回原因保留，刷新恢复会校验名单、判定和验收关联。旧工单不自动启用抽检。

验证：`npm run test:all`、`npm run test:sampling-browser`。这是本地原型的批次验收抽检，不宣称符合 AQL 或其他统计验收标准；仍要求先完成全部逐条审核，抽检由现有指定审核人执行，抽检仍由初审成员执行，服务端防篡改尚未实现。

### 三级独立审核（Issue #1，依赖 PR #11）

创建工单时可启用初审、复审、最终验收，三位审核人与标注人必须互不相同，且具备本项目及父来源的审核和退回权限。审核链在分派时固定；默认角色不足时，须先由管理员配置合适的项目成员授权，系统不会自动提高权限。旧工单维持单级流程。

初审在逐条审核、当前修订质检及已启用的抽检通过后提交结论，冻结记录和质量报告。复审及最终验收只能由当前指定成员依次完成，每级需填写结论，期间禁止原审核入口修改依据。只有最终验收通过才可发布。当前级别可以退回；返工或仲裁重新审核都需重新完成初审、复审与最终验收，并保留历史结论。审核链成员不能仲裁本工单争议，超时转派的标注人也不能与审核链成员冲突。

待办标明当前级别和责任成员；刷新恢复校验审批顺序、身份、冻结依据和最终验收关联。售后纠错继承来源工单的抽检策略、复审与最终验收成员，新初审成员由纠错分派指定并重新检查独立性和权限。成员停用或权限不足时拒绝继续，不自动换人或跳级。

验证：`npm run test:all`、`npm run test:approvals-browser`。当前为工单级可选固定三级审核，不含任意级数、项目策略模板、审批人代理/替换、服务端并发与不可篡改审计。

### 工单期限与人工超时处理（Issue #1，依赖 PR #12）

工单页显示期限内、24 小时内到期、已逾期和完成状态，提供由我处理、临期、逾期筛选，列表优先展示逾期工单。工作台待办同步显示期限和当前责任人：生产/返工由标注人处理，审核由当前级审核人处理，争议显示待独立仲裁。以浏览器时间每分钟更新，页面重新获得焦点或可见性变化时刷新；不写入虚假的通知发送记录。

负责人可为未完成工单延期，必须填写原因，新期限必须晚于原期限和当前时间。到达截止时刻即为逾期；待领取、生产中或返工工单可人工转派；部分样本已提交时保留其原标注人、内容与历史，只转派尚未提交的工作，已全部逐条提交但未交批次验收时也可转派后完成交接。待批次验收工单须先退回。延期与转派保留原/新期限、原/新标注责任人、操作人、原因和调整时是否已逾期，刷新恢复校验记录连续性。延期不会改变抽检、审核或生产状态。

已验收工单不再进入临期/逾期待办，也不能修改期限；完成状态按最后有效期限与实际验收时间判断，曾经发生的逾期延期记录仍保留。旧快照不会补造历史调整记录。

验证：`npm run test:all`、`npm run test:deadlines-browser`。此功能只提供浏览器内状态提示和人工处理；关闭页面后没有后台调度，不发送邮件、短信、桌面推送，也不自动改派。服务端时间、通知投递及审批人代理仍待后续实现。

### 跨流程复查记录（2026-10-29，PR #14 时点归档）

范围：PR #9–#13 的组合，以及原 Issue #1–#4 的完成定义。本次复查基线为 PR #13 的 `5d0e0ed69354e8bcf12c1bdd8acbd35ab60f8fad`；这些 PR 均仍为 open Draft、未合并。真实后端按用户要求暂停。此结论不等于整个平台已完成验收。

发现并修复：

1. 纠错补交再次被拒收时，已封存的纠错工单无法继续处理。现在从原反馈创建独立的新一轮纠错，以上一轮冻结交付为输入，继承抽检和多级审核策略，保留原工单、交付单与轮次记录。禁止从已拒收的反馈补交单另开旁路或重复提交同一纠错版本；已签收补交自身的新反馈仍可独立处理。
2. 第二轮补交完成后，上一轮拒收单仍残留在待办。现在已被新轮次接替的拒收单作为历史保留，待办跟随当前反馈；只有当前轮次补交签收后才能关闭反馈。
3. 快照恢复只检查部分交付引用，未核对完整冻结内容与签收证据。现在恢复时对照规范化的发布版本，并校验验收人、时间、对应历史与制作者隔离；原反馈、每轮纠错输入和历史补交的关联也会检查。此为本地一致性校验，不是服务端防篡改机制。
